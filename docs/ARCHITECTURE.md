# Architecture

## Goal

Keep voice intent provider-neutral while isolating Gemini-specific API details inside one adapter.

## R0 data flow

```text
request.json
   ↓
load_request
   ↓
VoiceRequest
   ↓
provider registry
   ↓
GeminiTTSProvider
   ├─ build_payload → dry-run / audit
   └─ generate      → provider network boundary
                         ↓
                    WAV bytes in memory
                         ↓
                    technical QC
                         ↓
                  atomic file write
                         ↓
                 SHA-256 receipt
```

## Layers

### 1. Request contract

Provider-neutral fields:

- model family selection
- transcript turns
- logical speaker names
- logical-to-provider voice bindings
- turn-level delivery style
- requested audio format

R0 intentionally supports only `audio/wav`.

### 2. Provider registry

The CLI resolves a provider through an explicit registry rather than importing Gemini-specific behavior into generic request validation.

Only `GEMINI` exists today.

### 3. Gemini adapter

The adapter:

- translates `VoiceRequest` into the current Gemini Interactions schema,
- attaches `speech_metadata.style` only when style exists,
- attaches `speech_metadata.speaker` to conversational turns,
- performs no network work while compiling a payload,
- lazily imports the optional Google SDK only at execution time.

### 4. Execution boundary

A provider request is allowed only when:

- the operator explicitly supplies `--execute`,
- the relevant API key exists,
- the request has already passed local contract validation.

Offline tests never cross this boundary.

### 5. Technical Audio QC

Before materialization, R0 checks that the generated bytes form a readable PCM WAV matching the current Gemini 3.8 unary default:

- 24,000 Hz
- mono
- 16-bit samples
- non-empty frames

Full-scale samples produce a warning rather than an automatic rejection.

### 6. Materialization

The output is written atomically in the destination directory. A failed technical QC result is not materialized to the requested final output path.

### 7. Receipt

The receipt records:

- schema version
- provider/model
- UTC generation timestamp
- SHA-256 of the provider request payload
- SHA-256 and size of output bytes
- safe request summary
- technical QC metadata

The receipt deliberately excludes:

- API keys
- full transcript text
- cookies/OAuth data

## Deliberate limitations

- Single-request conversational mode is capped at two speakers and R0 allows only the 30 curated Studio prebuilt voices in that mode.
- Voice replication is not implemented.
- Streaming output is not implemented.
- R0 supports WAV only.
- Provider voice IDs are adapter/config bindings, not canonical character identity.
- Semantic pronunciation/transcript verification is not yet implemented.
